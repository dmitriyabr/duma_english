# Retention gate: модель вместо календарных окон

## Проблема

Сейчас гейт промоушена (B1+) требует **наблюдённых** проб в окнах 7, 30, 90 дней: были ли повторные попытки по нодам в эти интервалы и с каким результатом. Чтобы появилась 90‑дневная проба, с момента якорной попытки должно реально пройти 90 дней — календарное ожидание не обойти. Это противоречит заявленному приоритету скорости и практике нормальных продуктов (Duolingo, CEFR по часам, а не по календарю).

## Идея: предсказание удержания по текущему состоянию

Не ждём N дней и не смотрим «была ли попытка в окне N». Считаем **предсказанное удержание на горизонте T дней** из уже имеющихся данных: текущий decayed mastery и half-life по ноде.

### Что уже есть в коде

- **mastery.ts:** по каждой ноде хранятся `masteryMean`, `decayedMastery`, `lastEvidenceAt`, `halfLifeDays`. Decay считается как  
  `decayedMastery = masteryMean * exp(-ln(2) * deltaDays / halfLife)`  
  (effective half-life растёт с числом повторений и надёжностью).
- По сути это та же семантика, что в Half-Life Regression (Duolingo): сила памяти убывает по экспоненте, half-life характеризует «полураспад» мастерства.

### Формула предсказания

- Сейчас: `decayedMastery` = мастерство «на сегодня» с учётом времени с последней попытки.
- Через T дней **без новых попыток**:  
  `predictedMastery(T) = decayedMastery * 2^(-T / halfLife)`  
  (это следует из той же экспоненты: ещё T дней decay).
- Интерпретация: если через T дней ученик не будет практиковать эту ноду, ожидаемое мастерство = `predictedMastery(T)`. Порог «удержал» у нас 70 — можно считать: **предсказанное удержание на T дней** = `predictedMastery(T) >= 70` (или в вероятностной форме: p_recall(T) ∝ predictedMastery(T)/100).

Таким образом мы получаем оценку «удержит через 7 / 30 / 90 дней» **без ожидания** этих дней — по текущему состоянию нод.

## Как использовать в гейте

1. **Область нод**  
   Либо те же ноды, что участвуют в bundle readiness для target stage (только релевантные для перехода), либо все ноды с direct evidence за lookback — как в текущем гейте. Логичнее для «готов к B1» брать ноды, которые засчитываются в бандлы текущего/целевого этапа.

2. **Данные**  
   Для выбранных нод нужны из `StudentGseMastery`:  
   `nodeId`, `decayedMastery`, `lastEvidenceAt`, `halfLifeDays`  
   (и при необходимости `evidenceCount`, `reliability` для effective half-life, если будем считать его отдельно от хранимого).

3. **Агрегат по горизонту T**  
   Для каждого горизонта T ∈ {7, 30, 90} (или только {7, 30} если 90 не хотим в гейте):
   - по каждой ноде: `predictedMastery(T) = decayedMastery * 2^(-T / halfLifeDays)` (с учётом effective half-life, если используем его);
   - считаем метрику, например:
     - **доля нод с predictedMastery(T) >= 70** (порог как сейчас), или
     - **среднее predictedMastery(T)** по нодам, и порог на среднее (например >= 70).
   - гейт по окну T: метрика >= порога и, при желании, минимальное число нод (чтобы не проходить по двум нодам).

4. **Решение гейта**  
   - Вариант A: заменить текущий «наблюдённый» гейт на модель полностью — high-stakes promotion только по предсказанному удержанию (7d, 30d, при необходимости 90d).
   - Вариант B: гибрид — например, требуем и «хотя бы немного наблюдённых проб в 7d» (чтобы модель не работала в пустоте), и предсказание на 30d. Тогда 90d можно не требовать вообще или только как предсказание.

Никакого календарного ожидания: ученик может пройти гейт, как только по текущему состоянию нод предсказанное удержание на 7/30 (и при желании 90) дней выше порога.

## Реализация (по шагам)

1. **Модуль предсказания**  
   - Файл, например `src/lib/retention/predictedRetention.ts`.  
   - Вход: список нод с `{ nodeId, decayedMastery, lastEvidenceAt, halfLifeDays }`, `now`, набор горизонтов `[7, 30, 90]`.  
   - Выход: по каждому горизонту T — `predictedRetentionRate` (доля нод с predictedMastery(T) >= 70) и/или `meanPredictedMastery(T)`, плюс при необходимости список нод ниже порога.

2. **Загрузка данных для гейта**  
   - Либо расширить выборку в `stageProjection` (или в `promotionGate`): кроме `AttemptGseEvidence` подтягивать `StudentGseMastery` по тем же нодам (или по нодам бандлов target stage), с полями `decayedMastery`, `lastEvidenceAt`, `halfLifeDays`.  
   - Либо отдельная функция `loadMasteryRowsForRetentionGate(studentId, targetStage)` возвращает список нод и их mastery state.

3. **Контракт гейта**  
   - В `promotionGate.ts`: добавить режим (или заменить текущий) «model-based»:
     - вызывать предсказание по mastery rows;
     - по каждому T считать passed = (метрика >= порога и minNodes при необходимости);
     - те же `blockerReasons` и структура результата, чтобы `stageProjection` и UI не ломались (например `retention_7d_below_threshold` / `retention_7d_insufficient_sample` можно переиспользовать, но семантика = «предсказание на 7d», а не «наблюдённая проба в 7d»).
   - Версию протокола обновить (например `retention-promotion-gate-v2` model-based).

4. **Тесты**  
   - Юнит-тесты: по фиксированным `decayedMastery`, `halfLifeDays` проверять формулу `predictedMastery(T)` и агрегат (доля выше 70, среднее).  
   - Интеграция: вызов гейта с mock mastery rows, проверка что passed/fail и blockerReasons соответствуют ожиданиям.

5. **Документация и конфиг**  
   - В blueprint / Gap Closure: retention gate для promotion = model-based (предсказание на 7/30/90 дней из текущего состояния); 90 дней — не календарное ожидание, а горизонт предсказания.  
   - При необходимости feature flag: «use model-based retention gate» чтобы переключать со старого гейта на новый.

## Итог

- **Как делать:** считать по текущим `decayedMastery` и `halfLifeDays` предсказанное мастерство через T дней: `predictedMastery(T) = decayedMastery * 2^(-T/halfLife)`; агрегировать по нодам (доля или среднее >= 70); использовать это в retention promotion gate вместо обязательных наблюдённых проб в календарных окнах.  
- **Что это даёт:** переход на следующий уровень не привязан к «подожди 90 дней» — только к текущему состоянию мастерства и спейсинга (уже заложенному в half-life и decay). Скорость сохраняется, при этом удержание по-прежнему учтено через модель.
